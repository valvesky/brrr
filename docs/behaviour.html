Behaviour

While automatic boost is on and at least one watched program is running, brrr asks for the performance mode. When the last one exits, it puts back what was there before.

The cycle

  1. brrr remembers the mode it found.
  2. It switches to the performance mode for this system. The mode is system-wide, so the whole machine runs that way, not only the watched program.
  3. When the last matching process exits, it restores the previous mode.

The tray and menu-bar status line is one of these sentences:

  • “Waiting for a build” when nothing watched is running.
  • “Boosting for …” followed by the names that are running.
  • “Automatic boost is off”.
  • “Paused after a manual change until … finishes”.
  • “The performance profile isn't available”.
  • “The configuration file has an error”.
  • “No power profile service”, or a more specific reason when the platform has one. On macOS, before you allow switching, that reason is “Allow brrr to switch power modes from its menu”.

The idle line says “build” even when the running program is not a compiler. A game you added is still announced by its process name on the boosting line. The Omarchy widget uses its own phrases for the same states: “Watching for commands”, “Performance requested”, “Off”, “Manual profile selection respected”, “Waiting for power-profiles-daemon”, and a note when process events are unavailable and it is polling.

A change you make yourself

If you undo the boost while a watched program is still running, brrr treats that as yours. It does not switch back to performance until those processes have finished. The icon says it is paused after a manual change. On the next run, after everything has exited, it will boost again.

The same rule protects a restore. brrr only puts back a mode that is still the one it set. If you have moved on, the saved undo is thrown away.

When performance is refused

Some machines and virtual machines have no performance mode. If the system refuses, brrr does not retry in a loop. It waits until the matching processes finish, and the icon says the performance profile is not available. The logged reason starts with performance hold rejected:.

One copy per user

Whichever brrr starts second waits about five seconds, so a restart can replace a copy that is still letting go of the mode, then exits with status 75. The message is that another instance is already running. The Omarchy widget reports the same thing.

Short-lived processes

A program that starts and exits very quickly can be missed, so brrr never boosts for it.

  • Linux prefers kernel process events, and also watches matched processes with pidfds so an exit is noticed even if an event is dropped. A recovery scan of /proc runs every five seconds. If events are unavailable, or you pass --poll, it scans every 500 ms instead. Very short-lived processes may still be missed. You do not need root.
  • Windows and macOS check the process list once a second. Anything that exits between two checks is invisible to that scan.

brrr counts processes you started, including, on Linux, ones that still carry your login uid after sudo, and on Windows ones in your logon session that you started as administrator. It does not count other users’ processes.

Windows, and the Balanced plan

The Power mode switch — Best performance, the slider under Settings › System › Power & battery — runs only while the Balanced plan is the active plan. That is the plan Windows 10 and 11 use unless you changed it. No administrator rights are required.

  • Balanced. brrr sets the Power mode overlay to Best performance, and writes down the overlay it replaced. If Best performance is already on, it changes nothing.
  • High performance or Ultimate performance. Those plans are already the fast ones. brrr leaves them alone.
  • Any other plan, such as Power saver. brrr switches the active power plan to High performance when that plan exists on the PC. If High performance is not installed, it changes nothing and reports that no performance power mode is available.

Unlike a Linux hold, a Windows power mode stays where it was set if a program crashes. While brrr is boosting it keeps windows-power-restore.json beside the config file, written before the change. Quit, shutdown, and the next start all restore from it, and only if the mode is still the one brrr set. A manual change is not overwritten. The installer asks a running brrr to quit before replacing or removing its files, so it can put the mode back first.

Linux

brrr asks power-profiles-daemon (or tuned-ppd) for a performance hold. The hold belongs to brrr’s system D-Bus connection, so the daemon drops it whenever brrr exits, including a crash. There is no restore file. Other applications’ holds, and system policy, can still affect the profile you actually get.

brrr follows daemon restarts and retries a release that fails. After an error it cannot recover from, it exits. The Omarchy plugin or a systemd unit with Restart=on-failure and RestartSec=5 starts it again within five seconds.

For one command you launch yourself, powerprofilesctl can take the hold before the command starts. That is separate from brrr:

powerprofilesctl launch --profile performance -- cargo build

macOS

brrr reads the current power source and the current settings with pmset -g, and changes only the source you are on, through the sudoers rule from install. Boosting means:

  • If Low Power Mode is on, turn it off.
  • On a Mac that has High Power Mode, turn it on. If the hardware rejects that, the rest of the change still stands and the rejection is logged.
  • If neither applies, nothing changes. The Mac is already at full power.

The same crash problem as Windows applies: pmset settings outlive the process. While boosting, brrr keeps macos-power-restore.json next to the config, and the next start repairs it if those settings are still the ones brrr wrote.
